# 精选刷新与历史展示超时修复

后台扫描已保存结果，页面仍可能在任务状态与展示读取处报 `context deadline exceeded`。每次展示读取原先都解析最近 100 轮大型 JSON，任务完成状态又携带完整结果；这些重复工作可能超过桌面端 15 秒请求期限，并占用 API 事件循环。

## 行为变化

- 任务完成只返回保存凭据和轮次、生成时间。前端再读取展示，并验证轮次或更新的生成时间，避免旧结果被标成新扫描。
- 短暂连接超时继续查询同一个任务，不重复提交扫描；累计等待仍有 30 分钟上限。页面提供“读取已保存结果”入口，重开页面可恢复未完成的查询。
- 展示变更检测只读取数据库元数据列。已有文件复用按时间、大小及文件身份失效的轻量投影缓存；未核验轮次才按需校验完整证据，单次最多 2 条。
- 首次升级会分批核对历史，独立的小型进度文件允许重启续查；页面提示尚待核对的数量。数据库编号和扫描开始时间都不能证明生成顺序，不据此跳过未核验的历史。进度文件绑定数据库身份，失败时重新核验，不阻止已有结果展示。
- 展示保留全部推荐、观察、证据不足原因及版本，省略重复原始证据。完整扫描文件和数据库记录保持原样，不删除历史、不改写旧推荐。
- 展示 JSON 在工作线程中编码，任务状态读取保持轻量，避免大型展示序列化阻塞状态及健康接口。
- 保留此前历史记录页先选轮次再读取 JSON 的性能修复。

## 验证方法与边界

回归测试使用 SQLite 列读取授权，禁止变更检测读取 `result_json`，同时禁止读取物理位置在大 JSON 之后的 `created_at`。合成大型记录验证归档完整、展示缩减、缓存失效与并发保存；人为阻塞展示编码时，健康和任务状态接口仍应响应。前端测试覆盖完成凭据、旧版本兼容、短暂超时、过期任务及迟到响应。

2026-11-03 对既有本地存档进行只读测量：旧历史查询在 15 秒预算内未完成；新版 100 条元数据查询热读约 3–4 毫秒。约 100 MB 存档的展示响应从约 37 MB 降至约 4.3 MB。单独读取该存档约 2.2 秒，缓存读取约 0.15–0.17 秒；首次升级还需要分批核对历史，不能将缓存速度当成升级首读速度。测试中一次核对 5 条大记录约需 9.7 秒，因此正式预算降为 2 条以留出请求余量。测量不包括首次 Python 模块导入，也不代表所有硬件和存档大小的性能保证。真实历史数据、日志与测量原件不进入仓库。

修复相关 Python 集成回归 162 项通过；预算从 5 降为 2 后，对受影响的缓存、响应性与展示测试再验 88 项通过。前端全量 159 项通过，Go 的异步刷新路由与关闭边界测试通过。源码无界面 HTTP 测试连续两次启动保留相同推荐身份和数量，展示读取期间健康与任务查询仍正常响应。

验证使用离线测试、服务端渲染和无界面的本地 HTTP 服务，不启动浏览器。此修复改善读取与任务恢复，不改变策略阈值，也不构成收益验证。
